# 10. Расположение в памяти и контрольные суммы

<a id="layout"></a>

## Почему нельзя просто сохранить структуру

Пусть есть структура с `u8` и `u32`. Она не обязана занимать ровно пять байтов. У типов есть **выравнивание** (*alignment*): требование к адресам, по которым их размещают. Между полями и в конце структуры могут появиться байты заполнения — **padding**.

```rust
#[repr(C)]
struct Header {
    tag: u8,
    length: u32,
}

fn main() {
    use std::mem::{align_of, size_of};
    let header = Header { tag: 1, length: 3 };
    assert_eq!(header.tag, 1);
    assert_eq!(header.length, 3);
    println!("u32 alignment: {}", align_of::<u32>());
    println!("Header size: {}", size_of::<Header>());
}
```

На платформе с четырёхбайтовым выравниванием `u32` после `tag` будет три байта padding, затем `length`; размер получится восемь. Это иллюстрация для указанного выравнивания, а не универсальная гарантия для всех платформ.

Без `repr(C)` используется стандартное представление Rust, и порядок полей в памяти не фиксируется порядком объявления. `repr(C)` задаёт правила расположения для взаимодействия с C, но не превращает структуру в переносимый файловый формат: остаются порядок байтов, целевые размеры и padding.

Справка: [представление Rust](https://doc.rust-lang.org/reference/type-layout.html#the-rust-representation), [представление C](https://doc.rust-lang.org/reference/type-layout.html#the-c-representation), [`size_of`](https://doc.rust-lang.org/std/mem/fn.size_of.html).

<a id="valid-values"></a>

## Произвольные байты не подходят любому типу

Любой восьмибитный узор допустим для `u8`. Для `bool` допустимы только представления false и true. У `char` ограничен диапазон допустимых скалярных значений. У ссылки должны быть выполнены требования к адресу, времени жизни, выравниванию и другим свойствам.

Поэтому преобразование произвольного буфера в структуру через указатель или `transmute` требует гораздо больше доказательств, чем «размер совпадает». Можно получить некорректное значение или прочитать неинициализированный padding. `repr(packed)` не устраняет все эти проблемы и добавляет риск невыровненных полей.

Для обычного двоичного формата достаточно `from_be_bytes`, `from_le_bytes`, проверяемых срезов и явного создания структуры из разобранных значений. В проекте ниже весь код обходится без `unsafe`.

Справка: [недопустимые значения и неопределённое поведение](https://doc.rust-lang.org/reference/behavior-considered-undefined.html#invalid-values), [`transmute`](https://doc.rust-lang.org/std/mem/fn.transmute.html).

<a id="zero-copy"></a>

## Представление без копии

Если декодер возвращает `&[u8]` для полезной нагрузки, сами байты не копируются. Это часто называют **zero-copy** в отношении данной операции. Однако чтение из сети в исходный буфер могло уже потребовать копирования, а маленькие числовые поля всё равно собираются в значения.

Такая оптимизация означает и ограничение: исходный буфер должен оставаться живым. Если сообщение надо положить в независимую очередь, иногда разумнее скопировать его в собственный `Vec<u8>` и упростить управление временем жизни.

<a id="crc"></a>

## CRC обнаруживает случайные повреждения

**Контрольная сумма** — компактный результат вычисления по данным. Она позволяет сравнить полученные байты с ожидаемыми. CRC использует операции над битами; разные варианты CRC отличаются параметрами, поэтому надпись «CRC32» сама по себе недостаточна для спецификации.

В проекте используется CRC-32/ISO-HDLC: отражённый полином `0xEDB88320`, начальное значение `0xFFFFFFFF`, финальная инверсия. Контрольный вектор: ASCII-байты `123456789` должны дать `0xCBF43926`.

```rust
fn crc32(data: &[u8]) -> u32 {
    let mut crc = 0xFFFF_FFFFu32;
    for &byte in data {
        crc ^= u32::from(byte);
        for _ in 0..8 {
            crc = if crc & 1 != 0 {
                (crc >> 1) ^ 0xEDB8_8320
            } else {
                crc >> 1
            };
        }
    }
    !crc
}

fn main() {
    assert_eq!(crc32(b"123456789"), 0xCBF4_3926);
    assert_eq!(crc32(b""), 0);
    assert_ne!(crc32(b"Rust"), crc32(b"rust"));
}
```

Это понятная учебная реализация, которая выполняет восемь шагов на байт. Реализации для высокой производительности могут использовать таблицы или специальные инструкции. Оптимизировать стоит после измерений, сохранив тестовые векторы.

CRC **не подтверждает отправителя и не защищает от намеренной подмены**: человек, изменивший данные, может пересчитать её. Для проверки подлинности нужны подходящие криптографические средства, например MAC или AEAD, и управление ключами. Также у контрольных сумм возможны совпадения для разных данных.

Справка по алгоритму и полиному: [RFC 1952, приложение с CRC](https://www.rfc-editor.org/rfc/rfc1952.html#section-8). Формат gzip в целом здесь не реализуется.

**Проверь себя.** Почему размер структуры не равен сумме размеров полей? Достаточно ли `repr(C)`, чтобы передать её сырые байты другой машине? Может ли CRC обнаружить каждое возможное изменение? Может ли она доказать, кто отправил сообщение?
