# 7. Безопасный разбор двоичных данных

<a id="parse-rules"></a>

## Парсер — это проверка правил

**Парсер** (*parser*) превращает байты в значения по спецификации формата. Ему недостаточно взять четыре байта и назвать их числом. Нужно проверить наличие данных, версию, допустимость флагов и длину полезной нагрузки.

Начнём с простого заголовка из четырёх байтов:

| Смещение | Размер | Смысл |
|---:|---:|---|
| 0 | 1 байт | Версия; допустима только 1 |
| 1 | 1 байт | Флаги; допустимы только биты 0 и 1 |
| 2 | 2 байта | Длина полезной нагрузки, `u16`, big-endian |
| 4 | Указанная длина | Произвольные байты |

Политика этого примера: вход содержит ровно одно сообщение; лишние байты считаются ошибкой. Для последовательности сообщений нужна другая политика — возвращать также непрочитанный остаток.

<a id="small-parser"></a>

## Полный маленький декодер

```rust
#[derive(Debug, PartialEq, Eq)]
enum ParseError {
    Truncated,
    Version,
    Flags,
    TrailingBytes,
}

fn parse(data: &[u8]) -> Result<(u8, &[u8]), ParseError> {
    let header = data.get(..4).ok_or(ParseError::Truncated)?;
    if header[0] != 1 {
        return Err(ParseError::Version);
    }
    let flags = header[1];
    if flags & !0b11 != 0 {
        return Err(ParseError::Flags);
    }
    let len = usize::from(u16::from_be_bytes([header[2], header[3]]));
    let payload = data.get(4..).ok_or(ParseError::Truncated)?;
    if payload.len() < len {
        return Err(ParseError::Truncated);
    }
    if payload.len() > len {
        return Err(ParseError::TrailingBytes);
    }
    Ok((flags, payload))
}

fn main() {
    let packet = [1, 0b01, 0, 3, 10, 20, 30];
    assert_eq!(parse(&packet), Ok((1, &[10, 20, 30][..])));
    assert_eq!(parse(&packet[..6]), Err(ParseError::Truncated));
    assert_eq!(parse(&[2, 0, 0, 0]), Err(ParseError::Version));
    assert_eq!(parse(&[1, 4, 0, 0]), Err(ParseError::Flags));
    assert_eq!(parse(&[1, 0, 0, 0, 9]), Err(ParseError::TrailingBytes));
}
```

Сначала `get(..4)` доказывает наличие заголовка. Поэтому следующие обращения `header[0]` и `header[3]` безопасны. Декодер не выделяет буфер для полезной нагрузки: он возвращает срез исходных данных.

Тип результата `(u8, &[u8])` связан временем жизни с входным `&[u8]`. По правилам сокращённой записи Rust понимает эту связь. Если исходный буфер уничтожен, вернуть ссылку на его часть нельзя. Для независимого результата понадобился бы `Vec<u8>` и копирование.

Проверка точной длины помогает найти рассогласование: отправитель обещал три байта, а прислал четыре. Это может быть ошибкой упаковки или неверным пониманием порядка байтов. Если формат намеренно допускает расширения, спецификация должна определить, как их читать.

<a id="parse-order"></a>

## Как выбирать порядок проверок

Удобный порядок: минимальная длина, сигнатура и версия, ограничения полей, заявленные длины, содержимое полезной нагрузки. Каждая следующая операция должна опираться на уже проверенные факты.

Если у поля длина `count * element_size`, сначала вычисляй её через `checked_mul`. Если конец равен `start + len`, используй `checked_add`. Сравни результат с размером входа и с лимитом приложения до выделения памяти.

Обычная ошибка — сначала сделать `vec![0; length_from_file]`, а затем проверить, приемлема ли длина. Проверка произошла поздно: память уже запрошена.

Паника из-за некорректного входного файла — плохой интерфейс парсера. `Result` позволяет пользователю увидеть причину, а программе продолжить работу. `unwrap()` в тесте с заранее известным корректным примером уместен; в декодере произвольного входа требуется обоснование каждой такой операции.

<a id="parser-tests"></a>

## Что тестировать

Для каждого поля нужны хотя бы корректное значение и нарушение его правила. Для длины важны 0, максимальное допустимое значение, слишком короткий вход и лишний хвост.

Тест `decode(encode(value)) == value` полезен, но два взаимно согласованных бага тоже могут пройти его. Дополняй такой тест заранее рассчитанными байтами: например, длина 258 должна кодироваться как `01 02` в big-endian.

Для короткого известного сообщения легко проверить каждое усечение: ни один собственный префикс не должен декодироваться как полный исходный пакет. В [проекте](11-project.md#project) такая проверка есть.

Справка по используемым операциям: [`slice::get`](https://doc.rust-lang.org/std/primitive.slice.html#method.get), [`u16::from_be_bytes`](https://doc.rust-lang.org/std/primitive.u16.html#method.from_be_bytes).
