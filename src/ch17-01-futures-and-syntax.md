<a id="futures-and-the-async-syntax"></a>

## Future и асинхронный синтаксис

Основные элементы асинхронного программирования в Rust — *future* и ключевые слова `async` и `await`.

*Future* представляет значение, которое ещё может быть не готово, но станет готовым в некоторый момент в будущем. Та же идея встречается во многих языках, иногда под названиями *task* или *promise*. В Rust основой служит типаж `Future`: он позволяет реализовывать разные асинхронные операции с помощью разных структур данных, объединённых общим интерфейсом. Future в Rust — это типы, реализующие типаж `Future`. Каждый такой объект хранит собственные сведения о ходе выполнения и о том, что для него означает готовность.

Ключевое слово `async` применяется к блокам и функциям и указывает, что их выполнение можно приостанавливать и возобновлять. Внутри асинхронного блока или функции ключевое слово `await` позволяет *ожидать future*, то есть ждать его готовности. Каждое место такого ожидания — возможная точка приостановки и последующего возобновления блока или функции. Проверка того, готово ли уже значение future, называется *опросом* (polling).

В других языках, например C# и JavaScript, тоже используются `async` и `await`. Если они вам знакомы, вы заметите существенные отличия в синтаксисе Rust. Как мы увидим, у этих отличий есть веские причины.

При написании асинхронного кода на Rust мы обычно используем `async` и `await`. Компилятор преобразует их в эквивалентный код с типажом `Future`, подобно тому как цикл `for` превращается в код с типажом `Iterator`. Но при необходимости `Future` можно реализовать и для собственного типа. Многие функции этой главы возвращают типы с собственными реализациями `Future`. В конце главы мы вернёмся к определению типажа и подробнее разберём его работу; пока этих сведений достаточно.

Всё это может показаться абстрактным, поэтому напишем первую асинхронную программу — небольшой сборщик данных с веб-страниц. Он получит два URL из командной строки, загрузит их конкурентно и вернёт результат того запроса, который завершится первым. В примере будет немало нового синтаксиса, но мы объясним всё по ходу дела.

<a id="our-first-async-program"></a>

## Наша первая асинхронная программа

Чтобы сосредоточиться на изучении асинхронности, а не на подборе компонентов экосистемы, мы создали крейт `trpl` — сокращение от The Rust Programming Language. Он реэкспортирует все необходимые типы, типажи и функции, главным образом из крейтов [`futures`](https://crates.io/crates/futures) и [`tokio`](https://tokio.rs). `futures` служит официальной площадкой для экспериментов с асинхронным кодом Rust; именно там изначально разрабатывался типаж `Future`. Tokio — наиболее широко используемая сегодня асинхронная среда выполнения Rust, особенно для веб-приложений. Есть и другие отличные среды, которые могут лучше подойти для ваших задач. Внутри `trpl` мы используем `tokio`, поскольку он хорошо проверен и широко применяется.

В некоторых случаях `trpl` переименовывает исходные API или оборачивает их, чтобы вы могли сосредоточиться на существенных для этой главы деталях. Чтобы понять устройство крейта, загляните в [его исходный код](https://github.com/rust-lang/book/tree/main/packages/trpl). Там видно, откуда взят каждый реэкспорт, а подробные комментарии объясняют работу крейта.

Создайте новый бинарный проект `hello-async` и добавьте зависимость `trpl`:

``` console
$ cargo new hello-async
$ cd hello-async
$ cargo add trpl
```

Теперь мы можем написать первую асинхронную программу с помощью компонентов `trpl`. Это будет небольшая утилита командной строки: она загрузит две веб-страницы, извлечёт из каждой элемент `<title>` и выведет заголовок той страницы, для которой весь процесс завершится раньше.

<a id="defining-the-page_title-function"></a>

### Определение функции page_title

Начнём с функции, которая принимает URL страницы, выполняет запрос и возвращает текст элемента `<title>` (листинг 17-1).

Файл: `src/main.rs`

``` rust
use trpl::Html;

async fn page_title(url: &str) -> Option<String> {
    let response = trpl::get(url).await;
    let response_text = response.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}
```

Листинг 17-1: Асинхронная функция для получения заголовка HTML-страницы

Сначала мы определяем функцию `page_title` и помечаем её ключевым словом `async`. Затем вызываем `trpl::get` для переданного URL и добавляем `await`, чтобы дождаться ответа. Чтобы получить текст `response`, вызываем метод `text` и снова ожидаем результат с помощью `await`. Оба шага асинхронны. Функция `get` ждёт, пока сервер пришлёт первую часть ответа: HTTP-заголовки, cookie и другие сведения, которые могут передаваться отдельно от тела. Получение всего тела, особенно большого, может занять время. Поскольку `text` должен дождаться ответа *целиком*, этот метод тоже асинхронный.

Оба future нужно ожидать явно: в Rust они *ленивые* и ничего не делают, пока вы не запросите это с помощью `await`. Более того, за неиспользуемый future компилятор выдаст предупреждение. Это напоминает итераторы из раздела [«Обработка последовательности элементов с помощью итераторов»](ch13-02-iterators.md) главы 13: они ничего не делают без вызова `next`, напрямую либо через цикл `for` или методы вроде `map`, использующие `next` внутри. Future тоже ничего не делает без явного запроса. Благодаря такой ленивости Rust не выполняет асинхронный код, пока тот действительно не понадобится.

> Примечание: это отличается от `thread::spawn` из раздела [«Создание нового потока с помощью spawn»](ch16-01-threads.md#creating-a-new-thread-with-spawn) главы 16: переданное потоку замыкание начинало работать сразу. Такой подход отличается и от асинхронности многих других языков. Но, как и в случае итераторов, он важен для гарантий производительности Rust.

Получив `response_text`, мы разбираем его в значение `Html` с помощью `Html::parse`. Вместо необработанной строки теперь есть структура данных для удобной работы с HTML. В частности, метод `select_first` ищет первый элемент, соответствующий CSS-селектору. Передав `"title"`, мы получим первый `<title>` документа, если он есть. Поскольку подходящего элемента может не быть, `select_first` возвращает `Option<ElementRef>`. Затем мы вызываем `Option::map`: он позволяет обработать значение внутри `Option`, если оно присутствует, и ничего не делать в противном случае. Здесь можно было бы использовать `match`, но `map` идиоматичнее. В переданной ему функции мы вызываем `inner_html` у `title`, получая содержимое в виде `String`. Итоговый тип — `Option<String>`.

Обратите внимание: `await` в Rust ставится *после* ожидаемого выражения, то есть является *постфиксным* ключевым словом. Если вы использовали асинхронность в других языках, это может быть непривычно, зато в Rust так удобнее строить цепочки методов. Поэтому тело `page_title` можно записать как цепочку вызовов `trpl::get` и `text` с `await` между ними, как в листинге 17-2.

Файл: `src/main.rs`

``` rust
    let response_text = trpl::get(url).await.text().await;
```

Листинг 17-2: Цепочка вызовов с ключевым словом `await`

Наша первая асинхронная функция готова! Прежде чем добавить её вызов в `main`, разберём подробнее, что именно мы написали.

Увидев *блок* с `async`, Rust превращает его в уникальный анонимный тип данных, реализующий `Future`. Увидев *функцию* с `async`, компилятор превращает её в обычную функцию, тело которой является асинхронным блоком. Возвращаемый тип асинхронной функции — анонимный тип, созданный компилятором для этого блока.

Таким образом, запись `async fn` эквивалентна функции, возвращающей *future*, результат которого имеет указанный тип. Для компилятора `async fn page_title` из листинга 17-1 примерно равнозначна следующей обычной функции:

``` rust
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}
```

Разберём преобразованную версию по частям:

- Здесь используется синтаксис `impl Trait`, рассмотренный в разделе [«Типажи в качестве параметров»](ch10-02-traits.md#traits-as-parameters) главы 10.
- Возвращаемое значение реализует `Future` с ассоциированным типом `Output`. Здесь `Output` равен `Option<String>` — тому же типу, который был указан в исходной асинхронной версии `page_title`.
- Всё тело исходной функции обёрнуто в блок `async move`. Блоки являются выражениями; весь этот блок и есть возвращаемое выражение функции.
- Как уже говорилось, асинхронный блок выдаёт значение `Option<String>`. Оно соответствует `Output` возвращаемого типа. В этом отношении блок ничем не отличается от ранее рассмотренных.
- Тело новой функции — именно `async move`, поскольку оно использует параметр `url`. Различия между `async` и `async move` мы подробно рассмотрим далее.

Теперь можно вызвать `page_title` из `main`.

<a id="executing-an-async-function-with-a-runtime"></a>

### Выполнение асинхронной функции с помощью среды выполнения

Для начала получим заголовок одной страницы, как в листинге 17-3. К сожалению, этот код пока не компилируется.

Файл: `src/main.rs`

``` rust
async fn main() {
    let args: Vec<String> = std::env::args().collect();
    let url = &args[1];
    match page_title(url).await {
        Some(title) => println!("The title for {url} was {title}"),
        None => println!("{url} had no title"),
    }
}
```

Листинг 17-3: Вызов `page_title` из `main` с аргументом, заданным пользователем

Мы получаем аргументы командной строки тем же способом, что и в разделе [«Приём аргументов командной строки»](ch12-01-accepting-command-line-arguments.md) главы 12. Затем передаём URL в `page_title` и ожидаем результат. Future выдаёт `Option<String>`, поэтому выражение `match` выводит разные сообщения в зависимости от наличия `<title>` на странице.

Ключевое слово `await` разрешено только внутри асинхронных функций и блоков, а специальную функцию `main` Rust не позволяет объявить асинхронной.

``` text
error[E0752]: `main` function is not allowed to be `async`
 --> src/main.rs:6:1
  |
6 | async fn main() {
  | ^^^^^^^^^^^^^^^ `main` function is not allowed to be `async`
```

Причина в том, что асинхронному коду нужна *среда выполнения* (runtime) — крейт Rust, управляющий подробностями исполнения такого кода. Функция `main` может *инициализировать* среду выполнения, но сама ею не является. Вскоре мы подробнее разберём почему. В любой программе Rust, исполняющей асинхронный код, есть хотя бы одно место, где создаётся среда для выполнения future.

Большинство языков с асинхронностью поставляются со встроенной средой выполнения, но Rust — нет. Вместо этого доступны разные среды с разными компромиссами, рассчитанные на разные задачи. Например, высокопроизводительному веб-серверу с множеством ядер и большим объёмом памяти нужно совсем не то, что одноядерному микроконтроллеру с малой памятью и без возможности выделять её в куче. Крейт среды выполнения часто предоставляет и асинхронные варианты обычных операций, например файлового и сетевого ввода-вывода.

Здесь и далее мы будем использовать `block_on` из `trpl`. Эта функция принимает future и блокирует текущий поток до его завершения. Внутри `block_on` создаётся среда выполнения на основе `tokio`, которая запускает переданный future. Поведение `trpl::block_on` похоже на одноимённые функции других сред. Когда future завершится, `block_on` вернёт полученное им значение.

Можно было бы передать future от `page_title` прямо в `block_on`, а затем разобрать полученный `Option<String>` через `match`, как мы пытались сделать в листинге 17-3. Но в большинстве примеров главы и в реальных программах выполняется больше одного асинхронного вызова. Поэтому передадим блок `async` и внутри него явно дождёмся результата `page_title`, как в листинге 17-4.

Файл: `src/main.rs`

``` rust
fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let url = &args[1];
        match page_title(url).await {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
    })
}
```

Листинг 17-4: Ожидание асинхронного блока с помощью `trpl::block_on`

Теперь программа ведёт себя так, как мы изначально ожидали:

``` console
$ cargo run -- "https://www.rust-lang.org"
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.05s
     Running `target/debug/async_await 'https://www.rust-lang.org'`
The title for https://www.rust-lang.org was
            Rust Programming Language
```

Наконец-то у нас есть работающий асинхронный код! Прежде чем устроить состязание двух сайтов, ненадолго вернёмся к устройству future.

Каждая *точка ожидания*, то есть место с ключевым словом `await`, позволяет вернуть управление среде выполнения. Для этого Rust должен сохранять состояние асинхронного блока: среда сможет заняться другой работой, а затем вернуться и снова попробовать продвинуть первую задачу. Получается скрытый конечный автомат — словно вы записали перечисление для сохранения текущего состояния в каждой точке ожидания:

``` rust
enum PageTitleFuture<'a> {
    Initial { url: &'a str },
    GetAwaitPoint { url: &'a str },
    TextAwaitPoint { response: trpl::Response },
}
```

Писать переходы между состояниями вручную утомительно и чревато ошибками, особенно когда позже добавляются новые возможности и состояния. К счастью, компилятор Rust автоматически создаёт структуры данных конечного автомата асинхронного кода и управляет ими. Обычные правила владения и заимствования для этих структур по-прежнему действуют. Компилятор проверяет их и выдаёт полезные сообщения об ошибках; с некоторыми из них мы ещё познакомимся.

Кто-то должен исполнять этот конечный автомат — этим занимается среда выполнения. Поэтому в описаниях сред вы можете встретить *исполнитель* (executor): так называется часть среды, отвечающая за исполнение асинхронного кода.

Теперь понятно, почему компилятор не разрешил сделать `main` асинхронной в листинге 17-3. Для исполнения future, возвращённого такой `main`, кто-то другой должен был бы управлять его конечным автоматом, но `main` сама является точкой входа программы! Вместо этого мы вызвали в ней `trpl::block_on`, создав среду и запустив future от блока `async` до завершения.

> Примечание: некоторые среды предоставляют макросы, с которыми *можно* написать асинхронную `main`. Макрос преобразует `async fn main() { ... }` в обычную `fn main`, выполняющую то же, что мы вручную сделали в листинге 17-4: вызывающую функцию, которая исполняет future до конца, как `trpl::block_on`.

Теперь объединим изученное и посмотрим, как написать конкурентный код.

<span id="racing-our-two-urls-against-each-other"></span>

<a id="racing-two-urls-against-each-other-concurrently"></a>

### Конкурентное состязание двух URL

В листинге 17-5 мы вызываем `page_title` для двух URL из командной строки и выбираем тот future, который завершится первым.

Файл: `src/main.rs`

``` rust
use trpl::{Either, Html};

fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let title_fut_1 = page_title(&args[1]);
        let title_fut_2 = page_title(&args[2]);

        let (url, maybe_title) =
            match trpl::select(title_fut_1, title_fut_2).await {
                Either::Left(left) => left,
                Either::Right(right) => right,
            };

        println!("{url} returned first");
        match maybe_title {
            Some(title) => println!("Its page title was: '{title}'"),
            None => println!("It had no title."),
        }
    })
}

async fn page_title(url: &str) -> (&str, Option<String>) {
    let response_text = trpl::get(url).await.text().await;
    let title = Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html());
    (url, title)
}
```

Листинг 17-5: Вызов `page_title` для двух URL и определение первого результата

Сначала мы вызываем `page_title` для каждого URL, заданного пользователем, и сохраняем future в `title_fut_1` и `title_fut_2`. Пока они ничего не делают: future ленивы, и мы ещё не начали их ожидать. Затем передаём их в `trpl::select`, которая возвращает значение, показывающее, какой из переданных future завершился первым.

> Примечание: `trpl::select` основана на более общей функции `select` из крейта `futures`. Та умеет гораздо больше, но связана с дополнительной сложностью, которую мы пока можем не рассматривать.

Любой future может законно «победить», поэтому возвращать `Result` здесь не имеет смысла. Вместо него `trpl::select` возвращает незнакомый нам пока тип `trpl::Either`. Он похож на `Result` наличием двух вариантов, но в нём нет встроенного смысла успеха и неудачи. Варианты `Left` и `Right` просто означают «одно или другое»:

``` rust
enum Either<A, B> {
    Left(A),
    Right(B),
}
```

Если первым завершается future из первого аргумента, `select` возвращает `Left` с его результатом; если из второго — `Right` с результатом второго. Это соответствует расположению аргументов в вызове: первый находится слева от второго.
