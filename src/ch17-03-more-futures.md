### Возврат управления среде выполнения

В разделе [«Наша первая асинхронная программа»](ch17-01-futures-and-syntax.md#our-first-async-program) мы узнали: в каждой точке ожидания Rust даёт среде возможность приостановить задачу и переключиться на другую, если ожидаемый future ещё не готов. Верно и обратное: Rust приостанавливает асинхронный блок и возвращает управление среде *только* в точке ожидания. Всё между такими точками выполняется синхронно.

Поэтому большой объём работы внутри асинхронного блока без точек ожидания мешает продвижению других future. Иногда говорят, что один future вызывает *голодание* остальных. В каких-то случаях это несущественно. Но при дорогостоящей подготовке, длительных вычислениях или бесконечном выполнении определённой работы необходимо подумать, когда и где возвращать управление среде.

Смоделируем длительную операцию, чтобы продемонстрировать голодание, а затем найдём решение. В листинге 17-14 вводится функция `slow`.

Файл: `src/main.rs`

``` rust
fn slow(name: &str, ms: u64) {
    thread::sleep(Duration::from_millis(ms));
    println!("'{name}' ran for {ms}ms");
}
```

Листинг 17-14: Имитация медленных операций с помощью `thread::sleep`

Здесь используется `std::thread::sleep`, а не `trpl::sleep`, поэтому `slow` блокирует текущий поток на заданное число миллисекунд. Эта функция заменяет реальные длительные блокирующие операции.

В листинге 17-15 мы вызываем `slow`, имитируя такую вычислительную работу в двух future.

Файл: `src/main.rs`

``` rust
        let a = async {
            println!("'a' started.");
            slow("a", 30);
            slow("a", 10);
            slow("a", 20);
            trpl::sleep(Duration::from_millis(50)).await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            slow("b", 10);
            slow("b", 15);
            slow("b", 350);
            trpl::sleep(Duration::from_millis(50)).await;
            println!("'b' finished.");
        };

        trpl::select(a, b).await;
```

Листинг 17-15: Вызовы `slow` для имитации медленных операций

Каждый future возвращает управление только *после* выполнения нескольких медленных операций. При запуске получится такой вывод:

``` text
'a' started.
'a' ran for 30ms
'a' ran for 10ms
'a' ran for 20ms
'b' started.
'b' ran for 75ms
'b' ran for 10ms
'b' ran for 15ms
'b' ran for 350ms
'a' finished.
```

Как и в листинге 17-5, где `trpl::select` выбирала победителя из двух загрузок URL, здесь `select` завершается сразу после `a`. Однако вызовы `slow` в двух future не чередуются. Сначала `a` выполняет всю свою работу до ожидания `trpl::sleep`, затем `b` выполняет свою работу до собственного ожидания `trpl::sleep`, после чего завершается `a`. Чтобы оба future могли продвигаться между медленными операциями, нужны точки ожидания для возврата управления среде. Значит, нам нужно что-то, что можно ожидать!

Такая передача управления уже видна в листинге 17-15: если убрать `trpl::sleep` в конце `a`, этот future завершится, а `b` *вообще не начнёт* выполняться. Для начала попробуем добавить `trpl::sleep`, позволяя операциям продвигаться поочерёдно, как в листинге 17-16.

Файл: `src/main.rs`

``` rust
        let one_ms = Duration::from_millis(1);

        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::sleep(one_ms).await;
            slow("a", 10);
            trpl::sleep(one_ms).await;
            slow("a", 20);
            trpl::sleep(one_ms).await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::sleep(one_ms).await;
            slow("b", 10);
            trpl::sleep(one_ms).await;
            slow("b", 15);
            trpl::sleep(one_ms).await;
            slow("b", 350);
            trpl::sleep(one_ms).await;
            println!("'b' finished.");
        };
```

Листинг 17-16: Использование `trpl::sleep` для поочерёдного продвижения операций

Между вызовами `slow` мы добавили `trpl::sleep` с ожиданием. Теперь работа двух future чередуется:

``` text
'a' started.
'a' ran for 30ms
'b' started.
'b' ran for 75ms
'a' ran for 10ms
'b' ran for 10ms
'a' ran for 20ms
'b' ran for 15ms
'a' finished.
```

Future `a` всё ещё успевает немного поработать до передачи управления `b`, поскольку сначала вызывает `slow`, а уже затем `trpl::sleep`. После этого переключение происходит при каждом достижении точки ожидания. Здесь мы поставили её после каждого `slow`, но работу можно разбить так, как удобнее для конкретной задачи.

В действительности нам не нужно *спать*: хочется продвигаться как можно быстрее. Нужно лишь вернуть управление среде. Для этого есть `trpl::yield_now`. В листинге 17-17 мы заменяем ею все добавленные вызовы `trpl::sleep`.

Файл: `src/main.rs`

``` rust
        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::yield_now().await;
            slow("a", 10);
            trpl::yield_now().await;
            slow("a", 20);
            trpl::yield_now().await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::yield_now().await;
            slow("b", 10);
            trpl::yield_now().await;
            slow("b", 15);
            trpl::yield_now().await;
            slow("b", 350);
            trpl::yield_now().await;
            println!("'b' finished.");
        };
```

Листинг 17-17: Использование `yield_now` для поочерёдного продвижения операций

Такой код яснее выражает намерение и может быть заметно быстрее, поскольку у таймеров, подобных используемому в `sleep`, обычно ограничена точность. Например, наша версия `sleep` всегда ждёт хотя бы миллисекунду, даже если передать `Duration` в одну наносекунду. А современные компьютеры *быстрые*: за миллисекунду они успевают многое!

Это означает, что асинхронность может быть полезна даже для вычислительных задач — в зависимости от того, чем ещё занята программа. Она помогает организовать взаимодействие частей программы, хотя за это приходится платить накладными расходами асинхронного конечного автомата. Такой подход называется *кооперативной многозадачностью*: каждый future сам решает, когда передать управление через точку ожидания, и сам отвечает за то, чтобы не блокировать выполнение слишком долго. В некоторых встроенных операционных системах на Rust это *единственный* вид многозадачности!

Конечно, в реальном коде обычно не ставят точку ожидания после каждого вызова функции. Передача управления относительно дешева, но не бесплатна. Во многих случаях дробление вычислительной задачи заметно замедляет её, поэтому для *общей* производительности иногда лучше ненадолго допустить блокировку. Всегда измеряйте, где находятся реальные узкие места программы. Но если работа, которую вы ожидали выполнять конкурентно, в основном идёт последовательно, об этом механизме стоит помнить.

### Создание собственных асинхронных абстракций

Future можно объединять в новые конструкции. Например, уже имеющихся компонентов достаточно для функции `timeout`. Получившийся компонент, в свою очередь, можно будет использовать для построения ещё более сложных асинхронных абстракций.

В листинге 17-18 показано, как мы хотим применять `timeout` к медленному future.

Файл: `src/main.rs`

``` rust
        let slow = async {
            trpl::sleep(Duration::from_secs(5)).await;
            "Finally finished"
        };

        match timeout(slow, Duration::from_secs(2)).await {
            Ok(message) => println!("Succeeded with '{message}'"),
            Err(duration) => {
                println!("Failed after {} seconds", duration.as_secs())
            }
        }
```

Листинг 17-18: Применение задуманной функции `timeout` к медленной операции с ограничением времени

Реализуем её! Сначала определим требования к API:

- Функция должна быть асинхронной, чтобы её можно было ожидать.
- Первый параметр — выполняемый future. Сделаем параметр обобщённым, чтобы подходил любой future.
- Второй параметр — предельное время ожидания. Тип `Duration` удобно передать в `trpl::sleep`.
- Результат — `Result`. Если future завершится вовремя, вернётся `Ok` с его результатом. Если раньше истечёт время, вернётся `Err` с длительностью ожидания.

Объявление показано в листинге 17-19.

Файл: `src/main.rs`

``` rust
async fn timeout<F: Future>(
    future_to_try: F,
    max_time: Duration,
) -> Result<F::Output, Duration> {
    // Here is where our implementation will go!
}
```

Листинг 17-19: Определение сигнатуры `timeout`

Типы соответствуют поставленной задаче. Теперь подумаем о *поведении*: переданный future должен состязаться с отсчётом времени. Функция `trpl::sleep` создаст future таймера, а `trpl::select` запустит его вместе с future пользователя.

В листинге 17-20 реализация `timeout` разбирает результат ожидания `trpl::select`.

Файл: `src/main.rs`

``` rust
use trpl::Either;

// --snip--

async fn timeout<F: Future>(
    future_to_try: F,
    max_time: Duration,
) -> Result<F::Output, Duration> {
    match trpl::select(future_to_try, trpl::sleep(max_time)).await {
        Either::Left(output) => Ok(output),
        Either::Right(_) => Err(max_time),
    }
}
```

Листинг 17-20: Реализация `timeout` через `select` и `sleep`

Реализация `trpl::select` не обеспечивает справедливость: она всегда опрашивает аргументы в порядке передачи. Другие реализации `select` могут случайно выбирать, кого опрашивать первым. Поэтому сначала передаём `future_to_try`, чтобы дать ему шанс завершиться даже при очень малом `max_time`. Если он завершится первым, `select` вернёт `Left` с его результатом. Если первым завершится `timer`, вернётся `Right` с результатом таймера `()`.

При `Left(output)` возвращаем `Ok(output)`. Если же таймер истёк и мы получили `Right(())`, игнорируем единичное значение с помощью `_` и возвращаем `Err(max_time)`.

Готово: работающая `timeout` построена из двух других асинхронных компонентов. При запуске после истечения времени программа выведет сообщение о неудаче:

``` text
Failed after 2 seconds
```

Поскольку future можно составлять из других future, из небольших асинхронных компонентов получаются мощные инструменты. Например, тем же способом можно совместить ограничение времени с повторными попытками, а затем применять их к сетевым операциям вроде запросов из листинга 17-5.

На практике вы чаще всего будете работать непосредственно с `async` и `await`, а функции вроде `select` и макросы вроде `join!` использовать для управления выполнением внешних future.

Мы рассмотрели несколько способов одновременно работать с несколькими future. Теперь познакомимся с *потоками значений* — способом работать с последовательностью future во времени.
