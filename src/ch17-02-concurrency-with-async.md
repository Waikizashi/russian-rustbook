<a id="applying-concurrency-with-async"></a>

## Конкурентное выполнение с помощью async

В этом разделе мы применим асинхронность к некоторым задачам конкурентного программирования, которые в главе 16 решали с помощью потоков. Поскольку основные идеи уже знакомы, сосредоточимся на различиях между потоками и future.

Во многих случаях асинхронные API конкурентного выполнения очень похожи на API потоков. В других случаях они заметно различаются. Даже если API выглядят похоже, их поведение часто отличается, а характеристики производительности различаются почти всегда.

<span id="counting"></span>

<a id="creating-a-new-task-with-spawn_task"></a>

### Создание новой задачи с помощью `spawn_task`

В разделе [«Создание нового потока с помощью `spawn`»](ch16-01-threads.md#creating-a-new-thread-with-spawn) главы 16 мы начали с двух потоков, выводящих последовательности чисел. Сделаем то же самое асинхронно. Крейт `trpl` предоставляет функцию `spawn_task`, похожую на `thread::spawn`, и функцию `sleep` — асинхронный аналог `thread::sleep`. Совместим их в примере со счётом из листинга 17-6.

Файл: `src/main.rs`

``` rust
use std::time::Duration;

fn main() {
    trpl::block_on(async {
        trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }
    });
}
```

Листинг 17-6: Новая задача выводит одну последовательность, пока главная задача выводит другую

Для начала вызовем в `main` функцию `trpl::block_on`, чтобы код верхнего уровня мог быть асинхронным.

> Примечание: с этого момента все примеры главы используют такую же обёртку с `trpl::block_on` внутри `main`. Мы часто будем опускать её, как и саму `main`. Не забывайте добавлять её в свой код!

Внутри блока запишем два цикла, каждый с вызовом `trpl::sleep`, который ждёт полсекунды — 500 миллисекунд — перед следующим сообщением. Один цикл находится в теле `trpl::spawn_task`, второй — в цикле `for` верхнего уровня. После вызовов `sleep` добавим `await`.

Поведение похоже на вариант с потоками: в том числе при запуске порядок сообщений в вашем терминале может оказаться другим.

``` text
hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
```

Эта версия прекращает работу, как только завершится `for` в главном асинхронном блоке: задача, созданная `spawn_task`, останавливается при выходе из `main`. Чтобы дождаться её полного завершения, нужен дескриптор ожидания. Для потоков мы вызывали `join`, блокируя выполнение до окончания потока. В листинге 17-7 то же можно сделать с помощью `await`, поскольку дескриптор задачи сам является future. Его `Output` — это `Result`, поэтому после ожидания мы также вызываем `unwrap`.

Файл: `src/main.rs`

``` rust
        let handle = trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }

        handle.await.unwrap();
```

Листинг 17-7: Ожидание дескриптора задачи через `await` до её завершения

Теперь программа работает до завершения *обоих* циклов:

``` text
hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!
```

Пока результаты асинхронного варианта и потоков похожи, а различия словно сводятся к синтаксису: `await` вместо `join` у дескриптора и ожидание вызовов `sleep`.

Но существенное отличие в том, что мы не создавали дополнительный поток операционной системы. Более того, здесь можно обойтись даже без создания задачи. Асинхронные блоки компилируются в анонимные future, поэтому достаточно поместить каждый цикл в свой блок и поручить среде выполнить оба до конца с помощью `trpl::join`.

В разделе [«Ожидание завершения всех потоков»](ch16-01-threads.md#waiting-for-all-threads-to-finish) главы 16 мы вызывали `join` у `JoinHandle`, возвращаемого `std::thread::spawn`. Функция `trpl::join` похожа на этот метод, но работает с future. Она принимает два future и создаёт новый, который после завершения *обоих* выдаст кортеж их результатов. В листинге 17-8 мы так ожидаем окончания `fut1` и `fut2`. Мы ожидаем не сами `fut1` и `fut2`, а новый future, созданный `trpl::join`. Результат игнорируется: это лишь кортеж из двух единичных значений.

Файл: `src/main.rs`

``` rust
        let fut1 = async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let fut2 = async {
            for i in 1..5 {
                println!("hi number {i} from the second task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        trpl::join(fut1, fut2).await;
```

Листинг 17-8: Ожидание двух анонимных future с помощью `trpl::join`

При запуске видно, что оба future выполняются до конца:

``` text
hi number 1 from the first task!
hi number 1 from the second task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!
```

Теперь порядок при каждом запуске будет одинаковым — в отличие от потоков и `trpl::spawn_task` в листинге 17-7. Причина в том, что `trpl::join` обеспечивает *справедливость*: поочерёдно опрашивает оба future одинаково часто и не даёт одному уйти вперёд, пока другой тоже готов. Для потоков операционная система решает, какой поток проверить и сколько времени ему дать. В асинхронном Rust выбор задачи делает среда выполнения. На практике всё сложнее: для управления конкурентностью среда сама может использовать системные потоки, и обеспечить справедливость бывает труднее, но всё же возможно. Среда не обязана гарантировать справедливость каждой операции; часто предлагаются разные API, позволяющие выбрать нужное поведение.

Попробуйте изменить ожидание future и посмотреть на результат:

- Уберите асинхронную обёртку вокруг одного или обоих циклов.
- Ожидайте каждый асинхронный блок сразу после его определения.
- Оберните в асинхронный блок только первый цикл, а полученный future ожидайте после тела второго цикла.

Дополнительное упражнение: попробуйте предсказать вывод каждого варианта *до* запуска!

<a id="sending-data-between-two-tasks-using-message-passing"></a>

### Передача данных между двумя задачами с помощью сообщений

Способ обмена данными между future тоже знаком: снова воспользуемся сообщениями, но теперь с асинхронными версиями типов и функций. Пойдём немного другим путём, чем в разделе [«Передача данных между потоками с помощью сообщений»](ch16-02-message-passing.md) главы 16, чтобы показать важные различия между конкурентностью на потоках и на future. В листинге 17-9 начнём с одного асинхронного блока, *не создавая* отдельную задачу, как раньше создавали поток.

Файл: `src/main.rs`

``` rust
        let (tx, mut rx) = trpl::channel();

        let val = String::from("hi");
        tx.send(val).unwrap();

        let received = rx.recv().await.unwrap();
        println!("received '{received}'");
```

Листинг 17-9: Создание асинхронного канала и сохранение его концов в `tx` и `rx`

Здесь используется `trpl::channel` — асинхронный вариант канала с несколькими отправителями и одним получателем из главы 16. Отличий немного: получатель `rx` изменяемый, а его метод `recv` возвращает future, который нужно ожидать, вместо непосредственного значения. Теперь можно передавать сообщения от отправителя получателю. Отдельный поток или даже задача не нужны: достаточно ожидать вызов `rx.recv`.

Синхронный метод `Receiver::recv` канала `std::mpsc::channel` блокирует выполнение до получения сообщения. Асинхронный `trpl::Receiver::recv` этого не делает: он возвращает управление среде выполнения до поступления сообщения или закрытия отправляющей стороны канала. Вызов `send`, напротив, мы не ожидаем, поскольку он не блокирует выполнение. Ему это не требуется: канал не имеет ограничения вместимости.

> Примечание: весь этот асинхронный код находится внутри блока, переданного `trpl::block_on`, и может избегать блокировки. Но код *снаружи* ждёт возврата из `block_on`. В этом и состоит назначение `trpl::block_on`: вы *выбираете*, в каком месте блокироваться до завершения асинхронного кода и где проходит граница между синхронным и асинхронным выполнением.

Обратите внимание на два обстоятельства. Во-первых, сообщение приходит сразу. Во-вторых, хотя мы используем future, конкурентности пока нет: всё выполняется последовательно, как и без future.

Сначала изменим первое: будем отправлять несколько сообщений с паузами, как в листинге 17-10.

Файл: `src/main.rs`

``` rust
        let (tx, mut rx) = trpl::channel();

        let vals = vec![
            String::from("hi"),
            String::from("from"),
            String::from("the"),
            String::from("future"),
        ];

        for val in vals {
            tx.send(val).unwrap();
            trpl::sleep(Duration::from_millis(500)).await;
        }

        while let Some(value) = rx.recv().await {
            println!("received '{value}'");
        }
```

Листинг 17-10: Отправка и получение нескольких сообщений через асинхронный канал с ожиданием паузы между сообщениями

Помимо отправки сообщения нужно получать. Здесь их число известно, и можно было бы четыре раза вызвать `rx.recv().await`. Но в реальной программе обычно ожидается *неизвестное* число сообщений, поэтому ждать нужно, пока не станет понятно, что больше их не будет.

В листинге 16-10 мы обрабатывали все значения синхронного канала циклом `for`. Но Rust пока не поддерживает `for` для *асинхронно выдаваемой* последовательности. Поэтому понадобится ещё не встречавшийся нам цикл с условием `while let`. Это циклический вариант конструкции `if let` из раздела [«Краткое управление потоком выполнения с `if let` и `let...else`»](ch06-03-if-let.md) главы 6. Цикл работает, пока заданный образец соответствует значению.

Вызов `rx.recv` создаёт future, который мы ожидаем. Среда выполнения приостанавливает future до готовности. При поступлении каждого сообщения результатом становится `Some(message)`. После закрытия канала, независимо от того, поступали ли вообще сообщения, результатом будет `None`: значений больше нет и опрос, то есть ожидание, следует прекратить.

Цикл `while let` объединяет эти действия. Если `rx.recv().await` возвращает `Some(message)`, сообщение доступно в теле цикла, как в `if let`. Если возвращается `None`, цикл заканчивается. После каждой итерации он снова достигает точки ожидания, и среда приостанавливает его до следующего сообщения.

Теперь все сообщения успешно отправляются и принимаются, но остаются две проблемы. Во-первых, сообщения приходят не с интервалом в полсекунды, а все вместе через две секунды — 2000 миллисекунд — после запуска. Во-вторых, программа никогда не завершается: она бесконечно ждёт новых сообщений. Остановить её придётся сочетанием Ctrl-C.

<a id="code-within-one-async-block-executes-linearly"></a>

#### Код внутри одного асинхронного блока выполняется линейно

Разберём сначала, почему сообщения приходят одновременно после всей задержки, а не поочерёдно с паузами. В одном асинхронном блоке порядок `await` в исходном коде соответствует порядку их выполнения.

В листинге 17-10 всего один асинхронный блок, и всё в нём выполняется линейно. Конкурентности по-прежнему нет. Сначала происходят все вызовы `tx.send`, чередующиеся с `trpl::sleep` и их точками ожидания. Только затем цикл `while let` доходит до ожиданий `recv`.

Чтобы пауза приходилась на промежуток между сообщениями, операции с `tx` и `rx` нужно разделить на два асинхронных блока, как в листинге 17-11. Тогда среда сможет выполнять их отдельно через `trpl::join`, как в листинге 17-8. И снова мы ожидаем результат `trpl::join`, а не каждый future по отдельности. Последовательное ожидание отдельных future вернуло бы нас к тому самому последовательному выполнению, от которого мы хотим уйти.

Файл: `src/main.rs`

``` rust
        let tx_fut = async {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;
```

Листинг 17-11: Разделение `send` и `recv` на отдельные блоки `async` и ожидание их future

Теперь сообщения выводятся с интервалом в 500 миллисекунд, а не все вместе через две секунды.

<a id="moving-ownership-into-an-async-block"></a>

#### Перемещение владения в асинхронный блок

Однако программа всё ещё не завершается из-за взаимодействия `while let` и `trpl::join`:

- Future от `trpl::join` завершается только после завершения *обоих* переданных future.
- `tx_fut` завершается после последней паузы, следующей за отправкой последнего сообщения из `vals`.
- `rx_fut` не завершится, пока не закончится `while let`.
- Цикл не закончится, пока ожидание `rx.recv` не даст `None`.
- Ожидание `rx.recv` даст `None` только после закрытия другого конца канала.
- Канал закроется при вызове `rx.close` или уничтожении отправителя `tx`.
- Мы нигде не вызываем `rx.close`, а `tx` не уничтожается до окончания внешнего асинхронного блока, переданного в `trpl::block_on`.
- Внешний блок не может закончиться, потому что ожидает завершения `trpl::join`, — и мы возвращаемся к началу списка.

Сейчас отправляющий блок лишь *заимствует* `tx`: для отправки владение не требуется. Но если *переместить* `tx` внутрь блока, он будет уничтожен при его завершении. В разделе [«Захват ссылок или перемещение владения»](ch13-01-closures.md#capturing-references-or-moving-ownership) главы 13 мы использовали `move` с замыканиями. Как обсуждалось в разделе [«Использование замыканий `move` с потоками»](ch16-01-threads.md#using-move-closures-with-threads) главы 16, при работе с потоками часто нужно перемещать данные внутрь замыканий. К асинхронным блокам применимы те же принципы, поэтому `move` работает с ними аналогичным образом.

В листинге 17-12 меняем отправляющий блок с `async` на `async move`.

Файл: `src/main.rs`

``` rust
        let (tx, mut rx) = trpl::channel();

        let tx_fut = async move {
            // --snip--
```

Листинг 17-12: Исправленная версия листинга 17-11, которая корректно завершается

*Эта* версия завершается после отправки и получения последнего сообщения. Теперь посмотрим, что нужно изменить для передачи данных из нескольких future.

<a id="joining-a-number-of-futures-with-the-join-macro"></a>

#### Ожидание нескольких future с помощью макроса `join!`

Наш асинхронный канал тоже поддерживает несколько отправителей. Чтобы отправлять сообщения из нескольких future, можно клонировать `tx`, как в листинге 17-13.

Файл: `src/main.rs`

``` rust
        let (tx, mut rx) = trpl::channel();

        let tx1 = tx.clone();
        let tx1_fut = async move {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx1.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        let tx_fut = async move {
            let vals = vec![
                String::from("more"),
                String::from("messages"),
                String::from("for"),
                String::from("you"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(1500)).await;
            }
        };

        trpl::join!(tx1_fut, tx_fut, rx_fut);
```

Листинг 17-13: Несколько отправителей в асинхронных блоках

Сначала клонируем `tx`, создавая `tx1` снаружи первого блока. Затем перемещаем `tx1` внутрь, как раньше перемещали `tx`. Исходный `tx` далее перемещаем в *новый* блок, который отправляет дополнительные сообщения с чуть большей задержкой. Мы расположили его после блока получения сообщений, но можно было и перед ним. Важен порядок ожидания future, а не их создания.

Оба отправляющих блока должны быть `async move`, чтобы при завершении уничтожались и `tx`, и `tx1`. Иначе мы снова получим исходное бесконечное ожидание.

Наконец, для дополнительного future заменяем `trpl::join` на `trpl::join!`. Макрос `join!` ожидает произвольное число future, если их количество известно при компиляции. Ожидание коллекции с заранее неизвестным количеством future мы обсудим позже в этой главе.

Теперь приходят сообщения от обоих отправляющих future. Поскольку задержки после отправки немного различаются, различаются и интервалы получения:

``` text
received 'hi'
received 'more'
received 'from'
received 'the'
received 'messages'
received 'future'
received 'for'
received 'you'
```

Мы рассмотрели обмен сообщениями между future, последовательное выполнение внутри асинхронного блока, перемещение владения в такой блок и совместное ожидание нескольких future. Далее обсудим, как и зачем сообщать среде выполнения, что она может переключиться на другую задачу.
