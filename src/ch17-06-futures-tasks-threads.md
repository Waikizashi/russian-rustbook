## Объединяем всё вместе: future, задачи и потоки

Как мы видели в [главе 16](ch16-00-concurrency.md), потоки выполнения — один из способов организовать конкурентное выполнение. В этой главе мы познакомились с другим: асинхронным кодом, future и потоками значений. Когда выбирать тот или иной подход? Ответ зависит от ситуации! Во многих случаях выбор стоит не между потоками *или* асинхронностью: нужны потоки *и* асинхронность вместе.

Многие операционные системы десятилетиями предоставляют модель конкурентного выполнения на основе потоков, поэтому её поддерживают и многие языки программирования. Однако у этой модели есть свои компромиссы. Во многих ОС каждый поток расходует заметное количество памяти. Кроме того, потоки доступны лишь тогда, когда их поддерживают операционная система и оборудование. В отличие от обычных настольных компьютеров и мобильных устройств, некоторые встраиваемые системы вообще не имеют ОС, а значит, и потоков.

Асинхронная модель предлагает другой, в конечном счёте дополняющий первый, набор компромиссов. В ней конкурентным операциям не нужны собственные потоки выполнения. Вместо этого они могут выполняться в задачах: например, в разделе о потоках значений мы запускали работу из синхронной функции с помощью `trpl::spawn_task`. Задача похожа на поток, но ею управляет не операционная система, а библиотечный код — среда выполнения.

Сходство API создания потоков и задач не случайно. Поток ограничивает набор синхронных операций; конкурентное выполнение возможно *между* потоками. Задача ограничивает набор *асинхронных* операций; конкурентное выполнение возможно как *между* задачами, так и *внутри* них, поскольку задача может переключаться между future в своём теле. Наконец, future — самая мелкая единица конкурентного выполнения в Rust, причём каждый future может представлять дерево других future. Среда выполнения, а точнее её исполнитель, управляет задачами, а задачи управляют future. В этом отношении задачи похожи на легковесные потоки под управлением среды выполнения, с дополнительными возможностями, которые даёт управление из среды, а не из ОС.

Это не означает, что асинхронные задачи всегда лучше потоков или наоборот. Конкурентное программирование с потоками в некоторых отношениях проще, чем с `async`. Это может быть как достоинством, так и недостатком. Потоки в некотором смысле работают по принципу «запустил и забыл»: встроенного аналога future у них нет, поэтому они просто выполняются до конца, а прерывать их может только сама операционная система.

При этом потоки и задачи часто отлично сочетаются: по крайней мере в некоторых средах выполнения задачи могут перемещаться между потоками. Более того, используемая нами среда выполнения, включая функции `spawn_blocking` и `spawn_task`, по умолчанию многопоточная! Многие среды используют подход *перехвата работы* (work stealing): незаметно для программы перемещают задачи между потоками в зависимости от их текущей загрузки, повышая общую производительность системы. Для этого подхода нужны и потоки, *и* задачи, а следовательно, и future.

Выбирая подход, ориентируйтесь на следующие практические правила:

- Если работа *хорошо распараллеливается*, то есть ограничена вычислительными ресурсами процессора, например при обработке большого набора данных, части которого можно обрабатывать независимо, лучше выбрать потоки.
- Если работа требует *много конкурентных операций*, то есть ограничена вводом-выводом, например при обработке сообщений от множества источников с разными интервалами и скоростями поступления, лучше выбрать асинхронный подход.

Если нужны и параллелизм, и конкурентное выполнение, выбирать между потоками и асинхронностью не обязательно. Их можно свободно сочетать, поручая каждому подходу то, с чем он справляется лучше. В листинге 17-25 показан довольно распространённый в реальном коде Rust пример такого сочетания.

Файл: `src/main.rs`

``` rust
use std::{thread, time::Duration};

fn main() {
    let (tx, mut rx) = trpl::channel();

    thread::spawn(move || {
        for i in 1..11 {
            tx.send(i).unwrap();
            thread::sleep(Duration::from_secs(1));
        }
    });

    trpl::block_on(async {
        while let Some(message) = rx.recv().await {
            println!("{message}");
        }
    });
}
```

Листинг 17-25: Отправка сообщений блокирующим кодом в потоке и ожидание этих сообщений в асинхронном блоке

Сначала мы создаём асинхронный канал, а затем запускаем поток, передавая ему владение отправляющей стороной канала с помощью ключевого слова `move`. В потоке отправляем числа от 1 до 10, после каждого засыпая на секунду. Наконец, как и на протяжении всей главы, запускаем future, созданный асинхронным блоком, который передаём в `trpl::block_on`. Внутри этого future ожидаем сообщения, как в других рассмотренных примерах передачи сообщений.

Вернёмся к сценарию из начала главы. Представьте, что набор задач кодирования видео выполняется в выделенном потоке, поскольку кодирование требует вычислений, а уведомление пользовательского интерфейса о завершении операций передаётся по асинхронному каналу. В реальных программах встречается бесчисленное множество подобных сочетаний.
